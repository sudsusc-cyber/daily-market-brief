# 日报运行预算

2026-09-03 调整，仅改变运行时间管理，不改变估值公式、邮件样式、收件人或发送计划。

- 正式日报和正式定向试发的 Actions job 硬超时均为 20 分钟。
- job 第一个步骤设置 `BRIEF_LLM_CUTOFF_EPOCH`，为该步骤启动后 17 分钟；依赖安装和状态恢复也消耗这段时间。目标是在硬超时前给渲染、SMTP 与收尾保留约 3 分钟。
- 主进程的 LLM 截止时间取“进程启动后 15 分钟”和上述 job 截止时间中较早者。未设置环境变量的本地运行使用 15 分钟上限；设置值损坏或已过期时不再发起 LLM 调用。
- 启用估值时，chat 与 search 共用累计 720 秒实际 API 耗时预算；未启用时为 480 秒。成功、失败及上层重试都计时，普通取数等待不扣 API 预算；但仍消耗绝对运行时间。
- 每次请求超时取原单次超时、剩余 API 预算、剩余绝对时间的最小值。预算耗尽返回已有降级错误，不重新启动预算、不无限重试。
- 日志 `llm.timing` 增加实际 API 耗时、累计预算、总经过时间和剩余时间。原 `llm.summary` 的 token/费用统计保留。
- 单次 token 上限、默认 SDK 零重试、费用估算方法和 ¥0.50 告警线不变。该费用线不是硬性扣费封顶；供应商账户余额、限流和实际账单不由此代码控制。

边界：这是 LLM 截止时间和目标收尾余量，不是对整个 Python 进程的可抢占截止保证。独立数据采集、渲染或 SMTP 故障仍可能耗尽余量，最终由 Actions 20 分钟硬超时约束。没有增加定时等待，正常完成时立即发送。

验证覆盖：模拟取数等待、成功/失败请求计时、chat/search 共享预算、剩余不足一秒、重试不能重置截止时间、过期/损坏环境配置以及两个工作流的一致性。测试不调用付费 API 或发送邮件。
