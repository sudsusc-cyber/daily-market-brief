# QQQM：历史净值逐交易日核对（v1.9）

日期：2026-09-04。只补取数和备用快照核验；邮件版式、乐观现金流公式、固定参数、IRR＝公允价值/现价−1 均不改变。

## 原因及证据

v1.8 的两次整包读取可以发现更新过程中的差异，但无法发现两次均返回“新日期＋旧净值”的稳定错配：此前只将 `/prices.effectiveDate` 当作 NAV 的日期。

从景顺 [QQQM 官方产品页](https://www.invesco.com/us/en/financial-products/etfs/invesco-nasdaq-100-etf.html) 的 Historic Prices 组件确认了公开历史净值接口：

`https://dng-api.invesco.com/cache/v1/accounts/en_US/shareclasses/46138G649/navs?idType=cusip&productType=ETF`

2026-09-04 实际回读的历史行：2026-09-02＝292.029084；2026-09-03＝295.446047。历史缓存中 NAV＝292.029084 却标为 9 月 3 日的输入包不合格。旧发送记录缺少完整原始 HTTP 响应，不能据此断言错配一定由景顺服务器造成。

9 月 3 日这组已核验输入 NAV＝295.446047、TTM PE＝28.61、远期配对＝27.79/21.35、TTM 分红＝1.3053，固定公式仍得 325.9526489556774；不是为保持 331 而改公式或锁住数字。

## 新闸门

1. 最近已收盘美股交易日由现有交易日历决定；历史 API 有周末/节假日沿用前值的记录，不能取第一行、最大日期或 HTTP 响应日期代替目标交易日。
2. 同时检查 CUSIP `46138G649`、USD 和唯一 `type=NAV` 序列。目标日必须恰好有一条记录；即使重复记录数值相同也拒绝，避免歧义。
3. `/prices.nav` 必须与该日历史行数值相同。两个官方接口均有六位小数，不用现价、舍入到分的价格或百分比容差替代净值。非有限数、布尔值、非正数、日期/币种/证券错误均拒绝。
4. 不禁止连续两个交易日 NAV 恰好相同；只检查各自的逐日来源，不能仅凭“和昨天一样”判错。
5. 每次整包读取均含历史核验，保留原两次整包一致性检查。历史记录缺失、不可读或错配时，不让 DeepSeek 用搜索引文覆盖这道校验，直接回退已有完整合格快照。

## 缓存和审计

- v1.9 / schema 3 快照保存匹配行、接口、标的、币种、日期、数值和历史响应的规范化 JSON SHA-256；匹配证据单独有完整性指纹。每次离线恢复均重新验证。完整历史序列不塞进 DeepSeek 提示词。
- `qqqm_calculation_audit.json` 的首次与复核来源包各自包含 `nav_history_evidence`。这是景顺同一发行方的两条不同数据路径，不冒充独立供应商；哈希用于追溯和损坏检测，不是供应商的数字签名。
- 旧快照不能无条件豁免。`config/qqqm_legacy_nav_evidence.json` 仅保存此次实读并核对过的 9 月 2、3 日历史行，用于一次性兼容旧 schema。既有 325.95 的正确完整包可保留，错配的 327.66 包会被排除；未核验过的其他旧日期不放行。
- 迁移文件不参与每日实时取数，不填补新字段，不刷新快照日期，不延长原 14 个自然日上限。现有 9 月 2 日备用底稿同样必须匹配历史行才能使用。
- 新增一次历史 API 请求与其他直取来源并发，两次整包合计新增两次小型 HTTP 读取，仍保留原超时、重试和阶段预算。来源齐全或历史核验失败时均不增加 DeepSeek 调用。

外部来源仍可能共同出错或同时不可用；本控制不保证数据永不出错，也不把该简化乐观模型等同于客观真实价值。
